## 一、根因结论

### 1.1 判定

| 项 | 结论 |
|---|---|
| **主因类别** | **类别 4：方案设计缺陷** |
| 次要类别 | **类别 2：上下文缺失**（平台侧"可注入/已生效"的验证通道尚未盘点清楚，导致 heuristic 结果不可验证） |
| 排除 | 类别 1（需求歧义）、类别 3（工具调用错误） |

### 1.2 判断依据

**排除类别 3（工具调用错误）**：同一条链路里任务能提交、能跑完、latent/视频输出形态正确，说明 `nodeInfoList` 的字段形态（`nodeId`/`fieldName`/`fieldValue`）、任务流转、结果拉取全部工作正常。若存在请求格式错误，任务会在提交阶段失败，而不是"悄悄用默认值跑完"。

**排除类别 1（需求歧义）**：需求（"把本地正/负提示词注入云端工作流并生效"）本身无歧义，问题出在实现机制的能力边界，不在需求理解。

**判定类别 4 的核心依据 —— 现有目标定位机制依赖的是"工作流形态约定"，而不是任何平台不变量：**

| 现有机制隐含的假设 | 假设的性质 |
|---|---|
| 承载采样语义的节点，`class_type` 字符串里包含 `sampler` | 命名约定（第三方自定义采样器随时可破） |
| 采样器 `positive`/`negative` 的**直接上游节点**自身就是带 `text` 字段的文本编码节点 | 拓扑形状约定（只要中间隔一个透传/条件变换节点即失效） |
| 提示词落点唯一、且必经 `positive`/`negative` 端口直连 | 单分支假设（条件汇聚、分支选择、多采样器均不符合） |
| 只要字段存在，注入就一定生效 | 违反平台明确规则（见 1.3） |

这三/四条不是"某个工作流的特殊情况"，而是**把一类工作流的形状写成了通用规则**——所以它天生不支持多工作流兼容。

### 1.3 平台侧的一条官方规则（本归属判断最关键的外援）

RunningHub 官方 `nodeInfoList` 说明明确写道（原文要点）：

- **「If a fieldName cannot be found in the API-format workflow, that means it's a purely front-end field」** → 可注入集合 = API-format 里存在的字段，不是 UI 上看到的字段。
- **「In API-format workflows, a fieldValue wrapped in `[]` typically indicates a connection (wiring) between nodes. It is not recommended to modify these values.」** → 被连线接管的字段，**平台明确不建议修改**。

  > ⚠️ **措辞校准（S1 取证后修正）**：本条官方原文**只说"不建议"，并未说明改了会怎样**。
  > 早期版本曾据此推断"注入会被上游值覆盖"，这属于**超出文档依据的推断**，
  > 在 [`platform-contract.md`](platform-contract.md) 事实 4 中被标为等级 C（未知）。
  > 不排除三种可能：(a) 覆盖生效、(b) 被上游覆盖（静默失效）、(c) 校验失败报 433/1101。
  > **因此不变量 A 必须继续强制** —— 它对三种情况都安全。

由此可推出通用设计时必须遵守的硬不变量，而当前实现只对第二条做了部分覆盖、第一条完全缺席：

- **不变量 A（可注入性）**：只把 `[]` 形态之外的**字面量字段**当作候选落点。
- **不变量 B（可达性）**：落点必须在**实际会被执行**的路径上（旁路/未选分支上的节点注入后不会被执行）。
- **不变量 C（存在性）**（S1 新增，官方错误码表取证）：`nodeId` / `fieldName` 若与工作流定义不一致，
  平台返回 **`803 APIKEY_INVALID_NODE_INFO`** 并在**提交阶段**硬失败。
  → 落点不存在时**不会静默通过**，这为显式绑定与漂移检测提供了零成本的负向验证通道。

### 1.4 本次失败的具体机制（仅作反例证据）

> 以下 id 仅用于本次复现与回归验证，**不得进入任何实现逻辑**。

本次工作流（Wan 2.2 14B I2V 官方模板，35 节点）具备三个同时出现的形态特征：

1. **条件链上存在透传型中间节点**：提示词编码节点 → 视频条件构造节点（它重新吐出 positive/negative/latent）→ 两个串联的 `KSamplerAdvanced`。
   → 现有兜底算法在拿到采样器的 `positive` 连线源后，要求该源节点自带 `text` 字段，否则放弃；于是**一路兜底+占位符扫描双双 0 命中**，不产生任何注入。
2. **工作流里不存在任何占位符标记**，且编码节点里写的是完整默认提示词 → 占位符主路径天然 0 命中，云端自然回落到默认值。
3. **大量参数由连线驱动 + 存在分支/旁路节点**：`steps`/`cfg`/`start_at_step`/`end_at_step` 全部经分支节点再进采样器；另有若干节点处于 bypass 状态。
   → 即使后续修好了提示词落点，**同一套"存在即可注入"的做法在标量参数上仍会静默失效**（打到 `[]` 字段上，或被未选分支吞掉）。

结论一句话：**不是这个工作流"特殊"，而是任何把「相邻、命名、存在」当 Rice 的实现，都会在这类形态上集体失效。** 这类形态（透传节点、分支选择、计算节点派生参数、多采样器、无占位符）恰恰是第三方工作流的常态。

## 二、业界对标：通用型节点是怎么做的

调研了 5 个同类实现，结论高度一致——**没有任何一家靠"推断"定位参数落点**：

| 实现 | 参数 addressing 方式 | 谁决定绑定关系 |
|---|---|---|
| **ComfyDeploy** | 工作流内插入 `External*` 输入节点，声明 `param_name` → API 传 `{input_name: value}` | **工作流作者显式声明输入 schema** |
| **RunComfy** | `overrides: {nodeId: {inputs: {field: value}}}`，以 `workflow_api.json` 为准 | **调用方显式指定** |
| **ViewComfy** | 官方脚本把 `workflow_api.json` 摊平成 `{nodeId}-inputs-{field}` 参数字典 | **暴露全量参数空间供调用方挑选** |
| **ComfyUI-Addoor / RHAPI** | `RunningHubNodeInfo` 由用户手填 node_id / field_name / field_value 并串联 | **调用方显式指定** |
| **PVL ComfyDeploy Universal** | 用户自填 10 组 name/value 对 | **调用方显式指定** |

两条共性，直接决定我们的架构方向：

1. **"输入模式"必须被显式化或全量暴露，而不是被猜。** 通用性的来源是"把参数空间暴露出来"，不是"把猜测规则写复杂"。
2. **静默失效是这个领域的已知通病**：ComfyDeploy 文档明确写了"name 不匹配会静默回退到默认值"，_Addoor 文档也写了"id 猜错则 override 静默无效"。→ 因此"可观测、可验证、不可验证即报错"不是加分项，而是这类产品的**核心差异点**，应当作为一等公民纳入架构（与本仓库既有的"杜绝静默失效"原则一致，只是要把它上升到"每个端口都要有状态"的粒度）。

## 三、架构优化方向（通用、无硬编码）

### 3.1 核心抽象：把"注入目标解析"从节点逻辑里剥离出来

引入独立的一层 **`Binding`（绑定）**：

```
SemanticPort（语义端口：positive / negative / seed / steps / cfg / width / …）
        ↓  Binding Resolver
StructuralSlot（结构槽位：nodeId + fieldName）   ← 唯一由平台理解的地址
```

- 节点层只负责产出 `(SemanticPort, value)` 意图，**永远不知道 nodeId**；
- 所有"知道怎么找 nodeId"的知识收敛到 Resolver；
- Binding 可被导出、审阅、锁定（lockfile），也可被用户直接覆盖。
- **Serving 不变**：最终仍以平台 `nodeInfoList` 形态提交。

### 3.2 三层能力模型（Discovery → Resolution → Verification）

| 层 | 职责 | 关键要求 |
|---|---|---|
| **D 发现层** | 从平台拿到"这个世界里都有什么"：完整节点与字段清单、每个字段是字面量还是连线引用（`[]`）、节点执行状态（bypass/mute）、可选：平台是否提供官方参数 schema | 输出**结构化快照**（Snapshot），可被缓存与 diff；字段一律标注 `value_kind ∈ {literal, link, unknown}` |
| **R 解析层** | 把 SemanticPort 解析为 StructuralSlot，且**给出证据路径与置信度** | 不依赖 `class_type` 名称、不依赖固定字段名白名单、不假设相邻距离；多候选时**必须裁决或上报**，不得默认取第一个 |
| **V 验证层** | 提交前后证明"注入真的被采纳了" | 提交前：语法/存在性/字面量性/可达性检查；提交后：拉取执行证据或做受控对照实验；任一环节无法验证 → 显式标注为"未验证"，不由责任心=安全性 |

### 3.3 解析层：有序解析器链（Resolver Chain）

按顺序尝试，每级可独立开关，**每级结果必须可解释**（为什么选中、依据哪条边）：

1. **R1 显式绑定（最高优先级）**
   用户在配置中声明 `workflow → {SemanticPort: (nodeId, fieldName)}`。零推断、可审计、100% 确定。
   → 只要这一层存在，**任意第三方工作流就已具备可用性**；其余各层只是降低配置成本。
2. **R2 平台契约**
   若平台提供"可暴露参数列表 / 参数 schema"，直接消费，视为权威。
3. **R3 作者意图（占位符协议，泛化为 token 字典）**
   扫描字面量文本中**任意** `{token}`，把发现的 token 自动变成可注入端口（不再只认 positive/negative 两个词）。这是最强的意图信号，但依赖作者配合——没有 token 时应明确产出"该工作流未声明参数协议"，而不是退化成猜。
4. **R4 结构求解（纯图分析，无类型/名称依赖）**
   - 构建数据流图；把「旁支/未选分支」节点标记为不可达；
   - 从**语义端口名**（positive/negative/latent_image/seed/…）反向切片，**穿越任意中间节点**，直到落在 `value_kind == literal` 的槽位；
   - 遇到**派生节点**（表达式/计算/swtich）时，沿其操作数继续上溯到可直接写入的字面量来源，并标注为"间接绑定"；
   - 遇到**多源汇聚**（条件合并）时：按策略"全部注入 / 上报歧义"，绝不自作主张取其一；
   - 严格遵守**不变量 A**（不向 `[]` 字段注入）与**不变量 B**（不在不可达路径上注入）。
5. **R5 交给人**
   无法唯一确定 → 输出候选清单 + 排序理由 + 一键固化到 R1 的路径；策略为"阻断或显式确认后放行"，保留项目既有的"不静默失效"红线。

### 3.4 三个必须补齐的横切机制

- **绑定漂移检测（Drift Guard）**
  云端工作流被编辑后 nodeId/拓扑会变。每次运行用 snapshot 指纹校验绑定是否仍然成立，漂移即告警并给出重新解析建议——这是"线上跑得好好的，某天突然不生效"的根治手段。
- **端口级状态回执（Receipt）**
  每个 SemanticPort 都要有终态：`RESOLVED → SUBMITTED → APPLIED_VERIFIED / APPLIED_UNVERIFIED / REJECTED / UNRESOLVED`，进 report 与前端可视化。
- **同一套规则覆盖手工通道**
  用户手写映射也必须过 R 层的校验器（存在性 + 字面量性 + 可达性），否则"绕过Resolver"会重新打开静默失效的口子。当前这条是缺的。

### 3.5 明确禁止项（评审 checklist）

实现中一旦出现以下内容即视为违背本方案：

- 任何 `class_type` 字符串包含判断（如 `"sampler" in name`）；
- 任何节点 ID 字面量、任何"某工作流的某某节点"分支；
- 任何除平台自身字段类型外的字段名白名单；
- 任何"相邻即可 / 距离固定 / 唯一即默认采用"的拓扑假设；
- 解析失败时静默跳过或默认落到第一个候选。

## 六、S2 落地与回退记录

### 6.1 落地过什么

`core/snapshot.py` 曾实现过完整的快照模型（字段形态标注 `value_kind`、节点执行态、
取值指纹 / 拓扑指纹、`diff_snapshots` 漂移检出），配 `tests/test_snapshot.py`。
同期的 `core/binding.py` 在其上做了显式绑定与漂移检测。

### 6.2 为什么移除（2026-10）

1. **没有消费方**：这两个模块是给「自动推断落点」路线打的地基。该路线在
   v1.3.x 被判定为**静默失效风险过高**（猜错落点 = 用户以为生效了，实际没送上去），
   已推倒为纯手动映射。地基失去了上层建筑。
2. **维护成本大于收益**：快照模型要跟着平台返回结构的变化持续适配，
   但当前没有任何代码路径依赖它。
3. 因此 `core/snapshot.py`、`core/binding.py`、`tests/test_snapshot.py`、
   `tests/test_binding.py` 一并删除，**没有任何替代实现**。

### 6.3 当前真正保留的

| 能力 | 位置 |
|---|---|
| 结构归一化（含 `_meta` 与节点标题） | `core/workflow.py:normalize()` |
| 占位符替换 | `core/workflow.py` + `core/mapping.py` |
| 映射逐条校验 / 803 定位 | `core/workflow.py:diagnose_injections()` |
| 显式绑定 | **不存在**——用 `node_overrides` 手工指定，等价于每次都显式绑一次 |
